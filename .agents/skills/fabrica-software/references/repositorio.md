# Operação no repositório

## E0 · Pré-requisitos e branch da feature

- Confirme a raiz com `git rev-parse --show-toplevel`, uma branch base com commit, `origin` e o resultado de `gh auth status`. Se `gh` estiver indisponível no `PATH` do Windows, teste `C:\Program Files\GitHub CLI\gh.exe` e registre o caminho funcional em `state.json.gh_path`. Solicite que a pessoa prepare os pré-requisitos ausentes. Verifique se `.specify/memory/constitution.md` está preenchida, sem tokens como `[PROJECT_NAME]`. A constituição é definida no projeto que receberá as features, usando `$speckit-constitution`.
- Para uma demanda nova, registre a branch base atual antes de acionar o Analista. Confirme `git status --porcelain` vazio. Se `.specify/feature.json` indicar outra feature, consulte o estado dela na branch correspondente. Inicie a próxima no mesmo diretório quando a anterior estiver `AGUARDANDO_MERGE`, `ENTREGUE` ou `CANCELADA`. Use um worktree separado para demandas simultâneas.
- A sessão principal controla o Git. Use a integração do Spec Kit sem extensão Git para manter criação de branch e commits com o orquestrador. Se o projeto já tiver hooks Git do Spec Kit, confira a compatibilidade antes de iniciar e mantenha as operações que mudam o repositório na sessão principal.
- Após `speckit-specify`, obtenha o diretório da spec pelo retorno da skill ou por `.specify/feature.json`. Use `BRANCH_NAME` quando a skill devolver esse valor. Na integração que retorna apenas `SPECIFY_FEATURE_DIRECTORY`, use o nome do diretório, como `001-hora-servidor`. Crie a branch a partir da base registrada e verifique que os arquivos da spec acompanharam a troca. Se a branch já existir, confirme que pertence à mesma feature antes de usá-la. Com uma colisão de identidade, pause e registre o conflito.
- Ao retomar uma spec, confirme a branch registrada em `state.json.branch` a partir do arquivo na própria branch e valide `git branch --show-current`. Trabalhe nela em E1 a E8. Controle o escopo da stage com `git diff --cached --name-only` e adicione somente os artefatos e as mudanças da rodada. Mantenha `.env`, chaves, certificados e credenciais fora dos commits.

## E7 e E8 · Publicação e merge

1. Use a autorização da pessoa para publicar no GitHub. Se ela disser para implementar até o PR na aprovação da spec ou em uma instrução posterior, use essa autorização. Em uma execução autorizada apenas localmente, deixe em `PUBLICANDO_PR` e registre que publicar é a próxima ação.
2. Sincronize a branch da feature com a base registrada antes de abrir ou atualizar o PR. Use `git fetch origin` e incorpore `origin/<base_branch>` na branch da feature via merge. Se houver conflito, delegue sua resolução ao Desenvolvedor e confira `git diff --check`, marcadores residuais e os comandos de verificação antes de concluir o commit. Mudanças da sincronização que exigirem correção seguem E4 a E6 e entram no orçamento de rodadas. Faça revisão e QA das mudanças que o merge introduzir na feature. Preserve o histórico publicado.
3. Faça push da branch da feature e abra o PR para `state.json.base_branch` com `gh pr create`. Se já houver PR da mesma feature, atualize-o. Registre a URL. Inclua na descrição o link da spec, requisitos e critérios cobertos, testes, pareceres, ressalvas, premissas e dependências novas.
4. Acompanhe os checks com `gh pr checks <pr> --watch`. Em falha, repasse os logs ao Desenvolvedor e repita implementação, revisão e QA antes de atualizar o PR. Se estiver confirmado que a CI não foi configurada, execute todos os comandos de verificação localmente e registre a ausência da CI no PR e no estado. Um check pendente permanece em acompanhamento. Registre `AGUARDANDO_MERGE` e a revisão humana pendente ao concluir E7.
5. No Checkpoint 2, apresente o PR à pessoa responsável pelo merge na base. Ao retomar, consulte `gh pr view <pr> --json state,mergedAt`. `MERGED` registra `merge_approval` aprovado e `ENTREGUE`. `OPEN` permite acompanhar ou tratar pedidos de mudança. `CLOSED` sem merge pede uma decisão da pessoa sobre cancelar ou retomar. O deploy fica a cargo do processo do projeto após o merge.

Registre o estado local nas pausas para retomada em nova sessão. Use apenas a branch da feature para salvar o estado. O fluxo da fábrica publica branches de feature e abre ou atualiza PRs. O merge do PR, o auto-merge e o deploy ficam fora da sua execução.
